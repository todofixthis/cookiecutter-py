# 005: Source the Template's Version from `__init__.py`, Matching Paddock

## Context

The template generates a static `version` field in `[project]` in
`pyproject.toml`, seeded from `cookiecutter.json`'s `version` key and later
bumped by the release skill's `uv version <version>`. `phx-paddock`, a newer
sibling project, instead declares `dynamic = ["version"]` and reads the
version from `__version__` in `src/paddock/__init__.py` via
`[tool.hatch.version] path = ...`. The five other sibling packages this
template already tracks — `filters`, `class-registry`, `filters-django`,
`filters-iso`, and `filters-pydantic` — all keep the static-field approach.

Separately, paddock's release skill gates `uv publish` on `keyring get
https://upload.pypi.org/legacy/ __token__` before running it, so a missing
credential is caught before the release's one irreversible step rather than
during it, handing the release back to the developer to supply
`UV_PUBLISH_TOKEN` themselves ([todofixthis/paddock#9][]). That gate only
works because `[tool.uv] keyring-provider = "subprocess"` is set — and all
five static-version siblings already carry that setting and an equivalent
gate, ported from paddock's fix alongside this template's own port of the
same release-skill fixes ([todofixthis/cookiecutter-py#2][]). This template
is the only sibling missing it — adopting it closes a gap the rest of the
family already closed, independent of which versioning convention is used.

The maintainer asked to adopt both — dynamic versioning and the keyring
config — for projects generated from this point forward.

## Options

The keyring-provider gap closes either way (see Context), so it isn't a
point of divergence between these options — both apply it. What differs is
the version field alone.

### Option 1: Do nothing

Keep the static `version` field and `uv version <version>` bumps.

**Pros:** Matches five of the template's six sibling packages.
**Cons:** Diverges from paddock, the most recently established reference —
future fixes to paddock's `release` skill that touch its version-bump or
tag steps (as the keyring-gate fix already did) need translating instead of
porting unmodified.
**Risks:** None beyond the status quo.

### Option 2: Read the version from `__init__.py` via `[tool.hatch.version]`, matching paddock (Accepted)

`dynamic = ["version"]` plus `[tool.hatch.version] path =
"src/{{ cookiecutter.package_name }}/__init__.py"` in `pyproject.toml`,
`__version__ = "{{ cookiecutter.version }}"` seeded into the generated
`__init__.py`. Update the release skill's version-bump step to edit
`__init__.py` directly instead of running `uv version`, and its tag step to
name `__init__.py` rather than `pyproject.toml`.

**Pros:** Matches paddock, so future fixes to paddock's release tooling
port here unmodified, the same way class-registry's `pyproject.toml`
structure let ADR 002 port its skills unmodified.
**Cons:** Diverges from the other five siblings — the template no longer
has one single sibling reference for its release tooling, and an existing
project already generated by this template doesn't get the migration
retroactively.
**Risks:** None beyond the Cons.

## Decision

Option 2, per the maintainer's direction. Paddock, not the five
static-version packages, is the template's reference going forward.

## Consequences

- The release skill's "Bump version" step edits `__init__.py` directly
  instead of running `uv version <version>`, and its "Tag and push" step
  points at `__init__.py` rather than `pyproject.toml` for what `<version>`
  must match.
- `pyproject.toml` gains `[tool.uv] keyring-provider = "subprocess"`, and
  the release skill's "Upload to PyPI" step gains the same keyring-check
  gate and stop-and-hand-back behaviour as paddock's and the five other
  siblings'.
- `cookiecutter.json`'s `version` key is unchanged — it still seeds the
  generated project's initial version, just into `__init__.py` instead of
  `pyproject.toml`.
