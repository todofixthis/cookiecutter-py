# 012: Generate a Path-Scoped Rule Naming Template-Owned Files

## Context

[ADR 008][] delivers each template release to generated projects as a Renovate PR. A
change made by hand to a template-owned file in one project either never reaches the
others, or turns the next update PR into a conflict. So an agent working in a generated
project has to know which files the template owns before it edits one.

An agent working in a generated project usually can't reach this repository, so it can't
check `template/` itself. It also tends to edit a file without first rereading AGENTS.md.

The maintainer asked for an end-to-end test of whether a harness-delivered hint would
work, recorded on [todofixthis/cookiecutter-py#11][]. Headless Claude Code ran against
baked projects, one run per case. The shipped configuration is a path-scoped rule plus a
one-line AGENTS.md pointer to it. With that configuration, the agent:
- held off adding a CI timeout to `build.yml` that every project needs, and proposed it
  for this repository instead;
- correctly still added a project-only dependency;
- correctly still rewrote a seed file.

In the comparison runs:
- **No guidance:** the agent made the CI edit in place.
- **Today's AGENTS.md section:** the agent also held off, but only after a lookup in this
  repository that needed approval. It then guessed which files the template owns.
- **The rule with no pointer:** the agent paraphrased the rule accurately without ever
  reading the rule file, so Claude Code loaded it when a listed file was read.
- **With the pointer:** the agent read the rule as a local file, with no approval needed.

The phx writing-adrs skill records that a rule loads only through the read tool. It
doesn't load on a shell read, or on a `Write` that creates a file unless a matching file
was read earlier in the session. This rule lists nearly every template file, so that
earlier read is likely. These runs didn't test either case.

## Options

### Option 1: Do nothing

AGENTS.md describes template ownership, and the agent checks `template/` at the recorded
`_commit` itself.

**Cons:** It costs a fetch and an approval each time, and it fails wherever this repository
is out of reach.
**Risks:** The agent guesses, and a template-wide change lands in one project.

### Option 2: Generate the rule here, and regenerate and check it in this repo (Accepted)

`scripts/template_owned.py` walks `template/`, following symlinks, and keeps the files git
tracks. It writes `template/.agents/rules/template-owned.md.jinja`:
- its `paths:` list holds every rendered path, under each symlinked spelling;
- it leaves out the seed files and `copier.yml`'s `_skip_if_exists` entries;
- its body names the seed files and gives the upstream-or-local test.

The `regenerate_template_owned` autohooks plugin regenerates and stages the rule when a
commit stages anything that could change it. A test fails when the committed rule differs
from the generator's output, and another checks a bake's rule against the baked files.

**Cons:** A new seed file has to be added to the generator's `SEED_FILES` by hand; until it
is, the file is listed as template-owned. The plugin only runs where autohooks is
activated.
**Risks:** An edit made only through the shell never triggers the rule. The edit tool
needs a prior read, which does trigger it, so the gap is shell-only changes such as
`uv add` to `pyproject.toml`, which are mostly project-only.

### Option 3: Compute the list in copier at render time

**Pros:** No generated file to keep in step.
**Cons:** Jinja can't list the template's files. Only `_tasks` or `_jinja_extensions` could,
and copier treats both as unsafe, which stops Renovate's untrusted `copier update`.

### Option 4: Broad globs in the rule

The rule lists patterns such as `.github/workflows/*` instead of exact paths.

**Pros:** Nothing to generate.
**Cons:** The globs also match project-only files, such as the extra workflow file the rule
tells a project to add for its own CI jobs. The rule would then wrongly send that file's
changes upstream.

### Option 5: A Claude Code PreToolUse hook in the generated settings

A hook in `.claude/settings.json` checks each Edit, Write or Bash call against the list and
injects the guidance.

**Pros:** Deterministic, including for a `Write` that creates a file before anything listed
was read.
**Cons:** It needs the same generated list plus a script that every project runs, and it
still misses arbitrary shell edits. It reaches only Claude Code.

### Option 6: An ownership banner in each template-owned file

**Pros:** Seen on any read, through any tool or harness.
**Cons:** It adds noise to every file, and some can't carry a comment (`renovate.json`,
`LICENCE.txt`).

## Decision

Option 2. The test showed the rule reaching the agent when it opens a listed file, with no
fetch from this repository, which is what Option 1 lacks. Option 3 can't be done safely.
Option 4 gives wrong instructions for project-only files, where exact paths can't. The
generator uses patterns only on its input side. Options 5 and 6 cost more for coverage the
shell-only gap doesn't justify; Option 5 is the step up if that gap proves real.

The test, not the plugin, is what enforces the rule. A session that can't run autohooks
still hits the staleness test in CI. The generator reads the git index, not the working
tree alone, so untracked files never reach a committed rule.

## Consequences

- AGENTS.md in a generated project shrinks to a pointer at the rule, so a harness that
  ignores `paths:` still learns where to look.
- The plugin runs first in the pre-commit list, so the pytest plugin sees the regenerated
  rule.
- The generator refuses a `SEED_FILES` entry naming no template file, and a
  `_skip_if_exists` entry that is a pattern, which its exact-match exclusion can't apply.
- A file under `template/` that isn't yet added to git is missing from the rule, while a
  local bake (which includes untracked files) has it. The bake test then fails locally
  until the file is added.
- Only one run per case backs the rule's effect, so a revision to its body should be
  re-tested the same way.
